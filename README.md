# CompassLink3D

An Android companion reads fused orientation from `SensorManager`, sends quaternions through an ADB reverse tunnel over USB, and drives a local PC dashboard with a 3D handset and live telemetry.

**ADB alone cannot supply live fused sensor data.** The companion app reads the sensors; ADB provides the USB transport. Streaming needs no Wi-Fi or internet. The initial tool installation and first Android build require internet to download dependencies. Subsequent streaming uses only the USB cable and PC loopback addresses.

## Quick start on Windows

Node.js 18 or newer must be installed. This workspace already has Node.js. Open PowerShell in the project folder:

```powershell
npm install
npm run setup:android
npm run build:android
```

Setup installs Microsoft OpenJDK 17, Gradle 8.9, Android command-line tools, platform-tools (ADB), Android platform 35 and Build Tools 34.0.0 into `.tools/`. It accepts the Android SDK tool licenses as part of installation. It does not replace your system Java. Build scripts select the local JDK and SDK for their own process. The Android plugins are pinned to AGP 8.7.3 and Kotlin 2.0.21. Android requires version 8.0/API 26 or newer and a rotation-vector sensor.

1. On the phone, enable Developer options (tap Build number seven times in Settings), then enable USB debugging. Settings names vary by phone.
2. Connect a **USB data cable**, unlock the phone, and accept the USB debugging authorization prompt.
3. Run `npm run connect`. It selects a USB device using `adb -d`, installs the debug APK, configures the reverse tunnel, and opens the companion. Connect exactly one USB debugging device.
4. Run `npm start` in a terminal and open [the local dashboard](http://127.0.0.1:8000).
5. Tap **Start streaming** on the phone. Keep the app in the foreground; it keeps the screen awake during streaming. Rotate the handset through all axes. Drag in the PC view to orbit the camera; double-click to reset the camera.

The debug APK is at `android/app/build/outputs/apk/debug/app-debug.apk` after a successful build. To stop, tap Stop streaming and press Ctrl+C in the PC server terminal. The Android app automatically stops when it leaves the foreground. Repeat `npm run connect` after reconnecting the cable if the tunnel is lost.

## Manual ADB commands

If using another ADB installation, put it on PATH or substitute its full path:

```powershell
adb devices -l
adb -d install -r android/app/build/outputs/apk/debug/app-debug.apk
adb -d reverse tcp:8765 tcp:8765
adb -d shell am start -n com.compasslink3d/.MainActivity
adb -d reverse --list
# Optional tunnel removal after stopping:
adb -d reverse --remove tcp:8765
```

`-d` selects USB and avoids selecting a wireless ADB connection. The app connects only to `127.0.0.1:8765` on the phone; the reverse rule forwards that to PC loopback port 8765. The dashboard server binds only `127.0.0.1:8000`. There are no remote JavaScript, font or CDN dependencies. Android's `INTERNET` permission is necessary for loopback TCP sockets even though streaming is offline.

## Android Studio

After setup, open `android/` in Android Studio. Set the Gradle JDK to the project's `.tools/jdk` (JDK 17). `android/local.properties` points to the project SDK and is generated by setup. The project includes a Gradle wrapper so the build version is reproducible. Select a connected phone and run `app`. Create the reverse tunnel before tapping Start streaming. The command-line build does not require Android Studio.

## Layout and behavior

| Location                                                            | Purpose                                                                           |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `android/app/src/main/java/com/compasslink3d/MainActivity.kt`       | Sensor registration, sample serialization, foreground lifecycle and phone UI      |
| `android/app/src/main/java/com/compasslink3d/UsbSensorTransport.kt` | Disposable connection sessions, reconnect, latest-sample queue and socket cleanup |
| `pc/server.js`                                                      | Loopback TCP receiver, bounded framing, validation, HTTP assets and state API     |
| `pc/dashboard.js`                                                   | Canvas phone renderer, camera controls, sequential polling and stale status       |
| `pc/orientation.js`                                                 | Quaternion math, coordinate mapping and Android orientation angles                |
| `pc/styles.css`                                                     | Responsive dashboard styling                                                      |
| `scripts/`                                                          | Tool setup, APK build and USB connection helpers                                  |
| `tests/`                                                            | Packet validation, TCP/API integration and orientation regressions                |

The PC runtime uses Node built-ins; Prettier is the only npm development dependency. Samples are requested at 50 Hz, and the sender transmits the latest available sample at up to 50 Hz. Slow connections drop superseded samples rather than accumulating latency. The dashboard polls sequentially about every 50 ms, draws the latest pose, and labels samples older than two seconds as stale. Socket inactivity is limited to ten seconds. Delivery and browser scheduling may reduce the observed rate.

## Coordinates and quaternion protocol

Android device axes are X right, Y toward the top edge, and Z outward from the screen. These axes follow the physical device's natural orientation, not its rotated UI. The handset mesh uses those same device coordinates. Android's rotation quaternion maps device vectors into East/North/Up world coordinates. The renderer first applies that quaternion, then maps world `(East, North, Up)` into view `(East, Up, -North)`, followed by an independent orbit camera. It does not accumulate Euler angles, so crossing 360 degrees does not cause pose discontinuities. `q` and `-q` render identically.

Heading, pitch and roll follow `SensorManager.getOrientation()` conventions; the heading is clockwise from magnetic north when the top edge projects onto the horizontal plane. Near vertical, heading is undefined and Euler angles have singularities; the 3D quaternion pose remains usable. Rotation-vector fusion and calibration depend on the phone. Nearby magnets and metal can affect heading. If `TYPE_ROTATION_VECTOR` is unavailable, the companion falls back to `TYPE_GAME_ROTATION_VECTOR`; its heading is relative and can drift because it does not use magnetic north.

The stream contains one UTF-8 JSON object per newline:

```json
{
  "t": 1730000000000,
  "timestampNs": "123456789000",
  "sensor": "android.sensor.rotation_vector",
  "accuracy": 3,
  "q": [0, 0, 0, 1]
}
```

`q` uses `[x,y,z,w]`, converted from Android's `[w,x,y,z]` output. The server validates finite components and normalizes them. `t` is phone wall-clock milliseconds; `timestampNs` is the monotonic sensor event timestamp, serialized as a string to preserve precision. The dashboard age uses PC receipt time and is not a measurement of cable latency. Accuracy codes are Android's -1/0/1/2/3 (no contact, unreliable, low, medium, high); availability varies by sensor. This version displays fused orientation, not separate raw accelerometer/gyro/magnetometer streams.

## Verification and maintenance

To remove installer ZIPs, extraction leftovers, interrupted downloads and generated build caches, run `npm run clean` with builds stopped. It keeps the source, installed tools, downloaded build dependencies and debug APK. The next Android build will take longer while it regenerates its caches. The dashboard can still be started normally with `npm start`.

```powershell
npm test
npm run build:android
npx prettier --check package.json pc tests
```

Tests validate quaternion normalization and invalid data rejection, fragmented TCP packets reaching the HTTP API, connection shutdown, asset serving, cardinal headings and coordinate mapping. Hardware verification requires a real phone: start streaming, rotate each axis, stop/restart repeatedly, unplug/reconnect USB and confirm automatic waiting/reconnection, and verify relative heading if the game sensor fallback is used. No phone measurements are simulated in the normal dashboard.

## Troubleshooting

- **Unauthorized/offline phone:** unlock it, accept the USB debugging prompt, check the cable, then rerun `npm run connect`.
- **Waiting for phone:** confirm `npm start` is running and the reverse rule exists. Run `.tools/android-sdk/platform-tools/adb.exe -d reverse --list`.
- **No supported sensor:** this phone exposes neither rotation-vector sensor. An emulator may lack realistic fused orientation.
- **Port already in use:** stop the other server using port 8000 or 8765 and restart CompassLink3D.
- **Heading moves unexpectedly:** move away from metal/magnets and follow the phone manufacturer's calibration guidance. Game sensor heading is relative.
- **Build download fails:** check internet access and retry setup/build. The `.tools` downloads and Gradle caches are local to this project. Offline streaming does not need access to those download servers.
